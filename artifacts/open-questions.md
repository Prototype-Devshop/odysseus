# Open Questions: Media Generation Provider Layer

> Companion to [`plan.md`](plan.md) and [`task-list.md`](task-list.md).
> Status values: `open` / `proposed` / `resolved`. Architect records; Forge/Infra/human decide.

| ID | Question | Why it matters | Proposed options | Owner | Status |
|----|----------|----------------|------------------|-------|--------|
| OQ-1 | What is the **source of truth** for the media model registry — the proposed `MediaModel` shape from the brief, the existing `ModelEndpoint` rows (`model_type="image"`), or a hybrid? | Determines how `list_media_models`/default resolution read data and whether existing image endpoints are auto-included. Affects every later slice. | (a) New registry list in settings JSON using the brief's `MediaModel` shape; (b) Derive from existing `ModelEndpoint` (`model_type="image"`) + `image_model` default; (c) Hybrid: registry references endpoint IDs + adds capabilities/workflow fields not on `ModelEndpoint` | Architect + Infra | open |
| OQ-2 | Where is **ComfyUI/provider config persisted** — extend `data/settings.json` (`DEFAULT_SETTINGS`), add a `ModelEndpoint` row variant, or a new small store? | Drives Slice 2/3/6 and whether Slice 6 settings work is needed at all. ComfyUI is not OpenAI-compatible, so a plain `ModelEndpoint` row may be a poor fit. | (a) `DEFAULT_SETTINGS` keys (e.g. `comfyui_endpoint_url`, `media_models`) — lowest footprint, admin-gated, scrub-aware; (b) `ModelEndpoint` row with new `provider`/`endpoint_kind` value; (c) dedicated table modeled on `ModelEndpoint` | Infra + human | open |
| OQ-3 | Which ComfyUI **HTTP endpoints** does the target build expose for probe, queue, status, and retrieval? | The provider module and probe (Slices 3/4) depend on the exact API. Assumed `POST /prompt`, `GET /history/{id}`, `GET /view`, probe via `/system_stats` or `/object_info`, but unconfirmed. | (a) Confirm against the user's ComfyUI instance (D1); (b) Default to documented ComfyUI API (`/prompt`, `/history`, `/view`, `/system_stats`); (c) Support a configurable probe path | Human + Forge | open |
| OQ-4 | How are **workflows** supplied and parameterized — bundled workflow JSON templates with prompt/param substitution, or a minimal hardcoded text-to-image graph for MVP? | Slice 4 generation flow + safety (R4). Brief lists workflow support as "Preferred", not "Required". | (a) MVP: one bundled text-to-image workflow JSON with known prompt/seed/size/steps/cfg fields to substitute; (b) Allow `workflowPath` per model (brief shape) loaded as untrusted data; (c) Both, starting with (a) | Forge + human | open |
| OQ-5 | Which **generation entry path** should ComfyUI use — the canonical owner-aware `src/ai_interaction.py` `do_generate_image()`, or the MCP `mcp_servers/image_gen_server.py` server (which currently omits owner/session on gallery insert)? | Avoids owner-scope leak (R2) and duplicated logic; keeps the `generate_image` return contract intact (A5). | (a) Route ComfyUI through `do_generate_image` (preferred — owner-aware) and have the MCP path delegate to it; (b) Implement in MCP server and fix its gallery insert to set owner/session | Forge + Infra | open |
| OQ-6 | Does the existing `gallery_images` table cleanly hold **media metadata** (provider, workflow, seed, width, height, model label), or is a minimal extension/sidecar needed? | Slice 5 (AC-8). Brief says if the store can't hold metadata cleanly, document nearest pattern and propose a minimal approach. | (a) Reuse existing columns (`prompt`, `model`, `size`, `width`, `height`) and fold extra fields into an existing JSON/`tags`-style column; (b) Add a small set of nullable columns; (c) JSON sidecar next to the image file | Infra + Forge | open |
| OQ-7 | Should there be a **unified degraded-state response shape** introduced here and reused (`list_media_models` + `generate_image`), given there is no shared degraded-state contract today? | Consistency/UX (R5, AC-3). Currently degraded states are ad hoc (`offline`/`empty`, `_format_upstream_error`, 503 strings). | (a) Define one small shape in the registry (provider, status, checked[], message, next_steps[]) and reuse; (b) Keep per-call-site ad hoc messages matching existing style | Architect + Forge | proposed |
| OQ-8 | How long should `generate_image` **wait/poll** for a ComfyUI job before returning a timeout, and should progress be surfaced via the existing tool progress callback? | Long jobs can stall the agent loop (R3). Cancel/retry and progress UI are out of scope. | (a) Bounded poll with a documented max wait + periodic progress via existing `progress_cb`; (b) Fixed conservative timeout, no progress | Forge + human | open |
| OQ-9 | For MVP, is **Slice 6 (settings UI) required**, or is configuration via existing endpoint/settings surfaces sufficient (UI deferred)? | Brief marks Slice 6 "only if needed" and forbids broad CSS/UI changes; affects scope. | (a) Defer UI; configure via existing admin settings/endpoint flow; (b) Add minimal settings controls reusing existing components | Human + Prism | open |
